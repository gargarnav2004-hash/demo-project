# PMPrep AI

## What this app is

PMPrep AI is an AI-powered practice tool for product manager interviews. A user
picks a question category, gets shown one interview question at a time, types
an answer, and receives a score (1-5) plus 2-3 specific feedback bullets
generated by Claude. Questions and grading rubrics are managed through an
`/admin` panel and stored in Supabase — no code changes needed to add,
edit, or delete a question, or to retune a rubric.

Practising requires a Clerk sign-in. `/` is a public landing page; every page
under the `(site)` route group shares a header with the brand link plus a
"Sign in" link (signed out) or Clerk's `UserButton` (signed in). "Start
practicing" sends signed-out visitors to `/sign-in?redirect_url=/practice`
and signed-in users straight to `/practice`; after signing in or up Clerk
returns them to `/practice`.

Flow: landing page `/` ("Start practicing") -> `/sign-in` or `/sign-up` if
signed out -> `/practice`: category selector (6 categories) ->
practice screen (one question with category + difficulty badges, textarea, submit) -> feedback panel (score +
bullets, with "Next question" / "Change category" actions).

Admin flow: `/admin/login` (password gate) -> `/admin` (Questions tab: add /
edit / delete questions with category + difficulty; Rubrics tab: edit the
grading criteria text per category). Changes are immediately visible on the
practice page since both read from the same Supabase tables.

## Tech stack

- Next.js (App Router, TypeScript, `src/` layout) + React
- Tailwind CSS v4 (theme tokens defined as CSS variables in
  `src/app/globals.css`, calm sage/off-white palette)
- `@anthropic-ai/sdk` for calling Claude from Next.js API routes (server-side
  only — the API key never reaches the client)
- `zod` + `@anthropic-ai/sdk/helpers/zod` (`zodOutputFormat`) for structured,
  schema-validated JSON output from Claude via `client.messages.parse()`
- `@supabase/supabase-js` for the `questions` and `rubrics` tables, accessed
  server-side only via the `service_role` key (never exposed to the client)
- `@clerk/nextjs` (v7) for end-user sign-in: `<ClerkProvider>` in
  `src/app/layout.tsx` (with `signInUrl="/sign-in"`, `signUpUrl="/sign-up"`,
  `afterSignOutUrl="/"`), `clerkMiddleware` in `src/proxy.ts`, `useAuth` /
  `UserButton` and the `<SignIn />` / `<SignUp />` components on the client,
  and `auth()` in the API routes.
  (`SignedIn`/`SignedOut` no longer exist in v7 — use `Show` or the hooks.)
- A single shared-password gate (`ADMIN_PASSWORD`) protects `/admin` and
  `/api/admin/*`, enforced in `src/proxy.ts` (Next.js proxy/middleware). It is
  separate from Clerk: admins do not need a Clerk account.
- `@vercel/analytics` — `<Analytics />` is rendered in `src/app/layout.tsx`;
  data shows up in the Vercel project's Analytics tab (must be enabled there)
- `posthog-js` for product analytics. It starts in
  `src/instrumentation-client.ts` and sends through the `/ingest` rewrite in
  `next.config.ts`, so ad blockers lose fewer events. Autocapture, session
  recording and surveys are off: only the events in `src/lib/analytics.ts` and
  pageviews are sent, and answer text never reaches PostHog.

## Where things live

- `src/types/index.ts` — `Category`, `Difficulty`, `Question`, `Rubric`,
  `FeedbackResult` types, plus the `CATEGORIES` tuple (Product Sense,
  Metrics, Estimation, Strategy, Behavioural, AI PM), `DIFFICULTIES`
  tuple (Easy, Medium, Hard), and the `MAX_ANSWER_LENGTH` (5000) input cap.
- `src/lib/analytics.ts` — `track(event, props)`, the typed list of PostHog
  events: `signed_up`, `question_started`, `answer_submitted`,
  `feedback_viewed`, `feedback_rated`.
- `src/components/PostHogIdentify.tsx` — mounted in the root layout. Calls
  `posthog.identify` with the Clerk user id only (no email or name),
  `posthog.reset` after sign-out, and sends `signed_up` once for an account
  created in the last 10 minutes, since Clerk has no client-side sign-up event.
- `src/lib/attemptsDb.ts` — `saveAttempt` and `setRating` for the `attempts` and
  `feedback_ratings` tables. `setRating` checks that the attempt belongs to the
  user.
- `src/lib/rateLimit.ts` — `checkRateLimit(req, route, limit)`: per-IP
  sliding-window limiter (60s window) used by the public API routes
  (`/api/question` 20/min, `/api/feedback` 10/min). Returns a `429` with
  `Retry-After`. It is in-memory, so on serverless each instance counts
  separately — a best-effort guard against casual abuse of the Anthropic
  key, not a hard cap. The daily limits below are the real cost cap.
- `src/lib/usageDb.ts` — `consumeAiCall(userId)` / `releaseAiCall(userId,
  usageDate)`: the daily Claude limits, stored in Supabase. Each user gets
  `USER_DAILY_LIMIT` (20) calls a day and the whole app gets
  `AI_DAILY_CALL_LIMIT` (default 300). Both reset at midnight IST.
- `supabase/migrations/` — numbered SQL files for every schema change since
  `schema.sql`, each run once by hand in the Supabase SQL editor. `0001`
  adds `usage_daily`, `app_usage_daily` and the atomic `consume_ai_call` /
  `release_ai_call` functions (executable by `service_role` only). `0002` adds
  `attempts` (every scored answer) and `feedback_ratings` (one thumbs up/down
  per attempt).
- `supabase/schema.sql` — one-time SQL to run in the Supabase SQL editor:
  creates `questions` and `rubrics` tables (with `updated_at` triggers and
  RLS enabled, no public policies — only the `service_role` key can read/
  write) and seeds them with the original 30 hand-written questions and
  6 category rubrics.
- `src/lib/supabase.ts` — lazily-constructed Supabase client, reads
  `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` from the environment. Throws
  a clear error if either is missing.
- `src/lib/questionsDb.ts` / `src/lib/rubricsDb.ts` — all reads/writes to
  the `questions` and `rubrics` tables go through these (used by both the
  public API routes and the admin API routes).
- `src/lib/anthropic.ts` — lazily-constructed Anthropic client, reads
  `ANTHROPIC_API_KEY` from the environment. Throws a clear error if the key is
  missing rather than silently failing.
- `src/lib/adminAuth.ts` — the admin cookie name and a `hashPassword` helper
  (Web Crypto `SHA-256`, works in both API routes and Edge proxy) used to
  turn `ADMIN_PASSWORD` into the cookie token.
- `src/proxy.ts` — default-exports `clerkMiddleware`, which runs on every
  request so `auth()` works in route handlers. Inside it, `/practice(.*)`
  is protected with `auth.protect()` (signed-out visitors are redirected to
  `/sign-in` with a return URL), and every `/admin/*` page and
  `/api/admin/*` route (except `/admin/login` and `/api/admin/login`) is
  gated behind a valid admin cookie; unauthenticated admin page requests
  redirect to `/admin/login` and admin API requests get `401`. The AI API
  routes are not matched here — they check the session themselves (below).
- `src/app/api/question/route.ts` — `POST { category, excludeIds }` picks the
  next question from Supabase at random (no Claude call). Returns `401` unless
  the caller has a Clerk session (checked before the rate limit and before any
  DB call). The routes return a JSON `401` rather than a redirect because they
  are called with `fetch()`.
- `src/app/api/feedback/route.ts` — `POST { questionId, answer }` loads the
  question from Supabase (never trusting question text from the browser) and
  scores the answer against the category's rubric. Same Clerk `401` check. Takes
  one call from the daily limits before calling Claude: over a limit it returns
  `429` with `code` `daily_limit` or `app_limit`, which `PracticeScreen` shows as
  a calm notice instead of an error. Saves the attempt and returns `{ score,
  bullets, attemptId }`; `attemptId` is null if the save failed, and the rating
  buttons are then hidden.
- `src/app/api/rating/route.ts` — `POST { attemptId, rating }` saves the user's
  thumbs up/down from `FeedbackRatingButtons`. Returns `404` for an attempt that
  isn't theirs.
- `src/app/api/admin/login/route.ts` / `.../logout/route.ts` — password
  check and cookie issuance/clearing.
- `src/app/api/admin/questions/route.ts` (list, create) and
  `.../questions/[id]/route.ts` (update, delete) — question CRUD.
- `src/app/api/admin/rubrics/route.ts` (list) and
  `.../rubrics/[category]/route.ts` (update) — rubric editing.
- `src/components/` — `Hero` (landing page content + "Start practicing"
  link), `SiteHeader` (brand + Sign in / `UserButton`), `PracticeFlow` (the
  `category` / `practice` state machine and which questions were already
  asked), `CategorySelector`, `PracticeScreen` (owns the
  answer/submit/feedback state for one question), `FeedbackPanel`.
- `src/components/admin/` — `QuestionsAdmin` (add/edit/delete with category +
  difficulty), `RubricsAdmin` (one editable textarea per category), and
  `ToastProvider` (`useToast()` -> `showToast("success" | "error", msg)`),
  mounted by `src/app/admin/layout.tsx` so every admin screen shows
  success/failure toasts for its actions.
- `src/app/(site)/` — route group (no URL segment) whose layout adds
  `SiteHeader`: `page.tsx` (`/`, public landing), `practice/page.tsx`
  (`/practice`, protected), `sign-in/[[...sign-in]]/page.tsx` and
  `sign-up/[[...sign-up]]/page.tsx` (Clerk `<SignIn />` / `<SignUp />`,
  `routing="path"`, `fallbackRedirectUrl="/practice"`). The admin pages sit
  outside this group, so they have no site header.
- `src/app/admin/page.tsx` / `src/app/admin/login/page.tsx` — the admin
  dashboard (Questions/Rubrics tabs + logout) and the password login screen.

## How the Anthropic API is used

Model: `claude-haiku-5-5` with thinking disabled (see `CLAUDE_MODEL` in
`src/lib/anthropic.ts`). It was chosen to make limited API credits last; it
scored strong answers about a point lower than `claude-opus-4-8` in a small
comparison.

Only `/api/feedback` calls Claude, using `client.messages.parse()` with
`output_config.format` set via `zodOutputFormat(...)`, so Claude's response
is validated against a Zod schema and returned as `response.parsed_output` —
no manual JSON parsing or prompt-based "respond only with JSON" hoping.

**Scoring** (`/api/feedback`): the category's rubric text is fetched from
Supabase and placed in the system prompt along with the question and the
user's answer. Claude returns `{ score: 1-5, bullets: string[] }`, validated by
`FeedbackSchema`. The API doesn't enforce array lengths and Haiku often returns
4 bullets, so the schema has no maximum and the route keeps the first 3.

If the limit check fails, the route returns a `500` without calling Claude. If
Claude fails for any reason, including the credits running out, the call is
given back to the daily limits and the route returns a `503` with a
plain-language message. Details go to the server log only.

## Rubric logic

Each category has a short, freeform grading-criteria string stored in the
`rubrics` table (seeded in `supabase/schema.sql`, e.g. Product Sense:
clarify the user, identify a real pain point, propose a focused solution,
consider how success is measured). This text is handed to Claude verbatim in
the system prompt for `/api/feedback` — there's no separate scoring
algorithm; Claude applies the rubric directly and returns the score/bullets.
Editing the text in the admin panel's Rubrics tab changes scoring behavior
immediately, with no deploy needed.

## Admin panel and auth

`/admin` is a single shared-password gate — there's no per-user accounts,
roles, or audit log. On login, `POST /api/admin/login` compares the
submitted password to `ADMIN_PASSWORD` and, on match, sets an `httpOnly`
cookie whose value is `SHA-256(ADMIN_PASSWORD)` (see `src/lib/adminAuth.ts`).
`src/proxy.ts` recomputes that hash from the current `ADMIN_PASSWORD` on
every request to `/admin/*` and `/api/admin/*` and compares it to the
cookie — so rotating `ADMIN_PASSWORD` invalidates all existing sessions.
This is intentionally lightweight (fine for a single-operator demo/internal
tool); it is not a substitute for real user auth if this is ever opened up
to multiple admins.

## Environment variables

- `ANTHROPIC_API_KEY` — required, read server-side only in
  `src/lib/anthropic.ts`.
- `AI_DAILY_CALL_LIMIT` — optional, Claude calls allowed per day across all
  users (default 300), read in `src/lib/usageDb.ts`.
- `NEXT_PUBLIC_POSTHOG_KEY` / `NEXT_PUBLIC_POSTHOG_HOST` — the PostHog project
  key (public by design) and ingest URL, e.g. `https://us.i.posthog.com`.
  Analytics stays off until both are set. Also add them in Vercel, with exactly
  these names.
- `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` — required, read server-side
  only in `src/lib/supabase.ts`. Use the `service_role` key (Project
  Settings -> API), not the `anon` public key — it's never sent to the
  client.
- `ADMIN_PASSWORD` — required to log into `/admin`.
- `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` / `CLERK_SECRET_KEY` — required for
  sign-in. Both must come from the SAME Clerk application (Clerk dashboard ->
  API Keys); a mismatched or mistyped secret key makes Clerk fail with
  `secret-key-invalid` / `clerk_key_invalid`. Also add them in Vercel.

Set these in `.env.local` (see `.env.local.example`). `.env*` is gitignored
by the default Next.js `.gitignore` (with an explicit exception for
`.env.local.example`), so real secrets are never committed.

## Database setup

Run `supabase/schema.sql` once in the Supabase project's SQL editor
(Project -> SQL Editor -> New query). It creates the `questions` and
`rubrics` tables and seeds them with the original question bank and
rubrics, so the practice app has content immediately. Then run each file in
`supabase/migrations/` once, in order. `/api/feedback` returns `500` until
`0001` has been run, so run migrations before deploying the code that needs them.

## Running locally

```
npm run dev
```

Requires `ANTHROPIC_API_KEY`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`,
`ADMIN_PASSWORD`, and the two Clerk keys in `.env.local`, and the Supabase schema applied (see
above).
